# Phase 0.5-B — Tenant-route security inventory: findings

Companion to [`route-security-manifest.json`](route-security-manifest.json) (the
machine-checkable source of truth — this document summarizes it for humans and
does not duplicate its 1,030 entries). Generated by
`scripts/route-inventory/extract-routes.ts` (AST-based route discovery over
`server/routes.ts` and `server/feedback-routes.ts`) and
`scripts/route-inventory/classify-routes.ts` (classification). Regenerate with
`pnpm route-inventory:generate`; verify with `pnpm route-inventory:check` or
`tests/route-manifest-completeness.test.ts`.

**Scope boundary:** this PR is inventory only. No runtime authorization,
middleware, or route handler changed. All findings below are deferred to
follow-up branches per the sequencing in
[`phase-0.5-launch-security-plan.md`](phase-0.5-launch-security-plan.md) (0.5r,
0.5s–0.5u).

- **1,030** routes discovered across `server/routes.ts` + `server/feedback-routes.ts`.
- **0** unclassified — every route received exactly one of the 9 categories.
- **0** duplicate or conflicting route ids.

## Confidence

| Confidence | Count | Meaning |
|---|---:|---|
| high | 64 | Matched an explicit, unambiguous signal (manual override, health/webhook path pattern, or an explicit `requirePlatformRole`/token check in the handler). |
| medium | 404 | Matched a route-level auth/scope signal but via a secondary heuristic. |
| low | 562 | No explicit tenant-scoping or auth-detail signal found in the route handler body itself — classified by elimination (authenticated, no stronger signal matched), **not** confirmed safe. |

**This is the single largest finding.** 562 of 563 `authenticated
global/self-service` routes are low-confidence. A representative sample —
`DELETE /api/absence-policies/:id`, `DELETE /api/accrual-accounts/:id`,
`DELETE /api/accrual-policies/:id`, `DELETE /api/agreement-templates/:id` — are
plainly company-owned resources by name, but the classifier found no
session/`companyId`/`enforceCompanyScope` signal *in the route handler
itself*, which most likely means scoping (if it exists at all) happens inside
a shared storage-layer helper the current AST pass doesn't trace into. This
inventory cannot distinguish "safe, scoped one level down" from "actually
unscoped" for these 562 routes — that is exactly 0.5r's job (extend
classification to trace storage-layer scoping, not just the route handler),
not this PR's.

## Client-supplied `companyId` without a membership check

**159 routes** read `companyId` from `req.query`, `req.body`, or `req.params`
with no `canAccessCompany()`/`assertUserCanAccessCompany()` call and no
`enforceCompanyScope()` middleware detected in the route. Sample:
`DELETE /api/tenants/:id/companies/:companyId`, `GET /api/1099-summaries`,
`GET /api/1099-summaries/export`, `GET /api/accrual-accounts`,
`GET /api/agreement-templates`, `GET /api/app-doctor/repair-tickets`,
`GET /api/app-doctor/reports`, `GET /api/audit-log`. Full list:
`findings.clientSuppliedCompanyIdWithoutMembershipCheck === true` in the
manifest. This is the concrete input list for 0.5r/0.5s — each one needs a
human read of its actual query/storage layer (this pass only looked at the
route handler source) before any enforcement change.

Of the 159: 148 are `authenticated tenant-scoped` (expected — these are the
routes the category exists for, and the finding says the *route handler*
itself doesn't gate on it, which is normal if a lower layer does), 9 are
`platform-console only` (plausibly legitimate — platform routes are expected
to cross tenants — but unreviewed), 2 are `internal diagnostics/health`.

## Platform-role allowlist inconsistency

Among the 19 `platform-console only` routes, the `requirePlatformRole(...)`
role-argument sets are **not uniform**:

- 16 routes carry no role args captured directly on the route (gated instead
  by a mount-level `app.use("/api/...", requirePlatformRole(...))` allowlist,
  e.g. `GET /api/feature-registry`, `GET /api/feature-registry/log`,
  `GET /api/feature-registry/tenant/:companyId`, `GET /api/provisioning/templates`,
  `GET /api/provisioning/tenants`).
- 2 routes require `["platform_admin", "platform_super_admin"]`.
- 1 route requires only `["platform_super_admin"]`.

This confirms plan-doc finding **PT2**: there is no single canonical
platform-role allowlist, and `expandRoleForGuard` (`server/routes.ts:260-279`)
gives `platform_owner`/`platform_super_admin`/`platform_admin` blanket
tenant-admin-equivalent access with no boundary between "platform owner
operating their own tenant" and "platform owner accessing any other tenant."
Defining the fail-closed platform-vs-tenant boundary helper is 0.5u's
deliverable, not this PR's.

## CSRF classification

No CSRF protection mechanism exists anywhere in this codebase today (confirmed
by direct search — zero `csrf` hits under `server/`; re-confirms plan-doc
finding **T6**). Every mutating (non-`GET`) route was therefore classified by
what *would* need CSRF coverage once a mechanism exists:

| CSRF classification | Count | Meaning |
|---|---:|---|
| not-applicable | 373 | Non-mutating (`GET`) route. |
| unprotected-needs-classification | 651 | Mutating route, no CSRF mechanism exists yet — needs coverage once 0.5c (shared CSRF + rate-limit middleware) lands. |
| webhook-signature-not-csrf | 6 | Mutating, but protected by signature/secret verification instead of session-cookie CSRF (webhook/callback routes). |

This is an inventory, not a fix — 0.5c defines and lands the actual
middleware; this manifest is the checklist of what needs to adopt it.

## Deferred follow-ups (not fixed in this PR)

2. **0.5r/0.5s** — human review of the 159 client-supplied-`companyId`
   routes; add cross-tenant negative tests (disposable PostgreSQL only, see
   plan doc) for any confirmed gap.
3. **0.5u** — define the fail-closed platform-owner-vs-tenant-membership

4. **0.5c** — land shared CSRF + rate-limit middleware; then re-run this
   inventory's CSRF classification to confirm the 651
   `unprotected-needs-classification` routes have adopted it.
