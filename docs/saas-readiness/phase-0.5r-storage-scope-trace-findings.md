# Phase 0.5r — Storage-layer tenant-scoping trace: findings

Companion to [`storage-scope-trace-manifest.json`](storage-scope-trace-manifest.json)
(machine-checkable source of truth — this document summarizes it and does not
duplicate its 721 entries). Generated by
`scripts/storage-scope-trace/extract-storage-methods.ts` (AST index of every
`DatabaseStorage` method in `server/storage.ts`) and
`scripts/storage-scope-trace/trace-routes.ts` (per-route trace). Regenerate
with `pnpm storage-scope-trace:generate`; verify with
`pnpm storage-scope-trace:check` or
`tests/storage-scope-trace-completeness.test.ts`.

**Scope boundary:** audit only. No runtime authorization, storage method, or
route handler changed. No schema, environment, database, billing, tenant, or
user data touched. No live database was used — this is entirely static
source analysis.

## What this trace adds over Phase 0.5-B

[0.5-B](phase-0.5-b-route-inventory-findings.md) classified every route from
signals visible *in the route handler itself* and left 562
`authenticated global/self-service` routes at low confidence — no scoping
signal was found in the handler body, which could mean either "actually
unscoped" or "scoped one level down, in the storage layer, which 0.5-B didn't
inspect." This trace takes exactly one more static hop: it re-parses each of
those 562 routes' handler bodies (plus the 159 routes separately flagged for
taking a client-supplied `companyId`) for `storage.<method>(...)` calls and
inline `db.<verb>(...)` queries, resolves each `storage.<method>` against a
fresh AST index of all 727 `DatabaseStorage` methods, and checks whether that
call's own query filters by a `companyId`/`tenantId` column.

**Target set: 721 routes** (562 low-confidence-global-self-service ∪ 159
client-supplied-companyId; the two sets do not overlap).

## Disposition totals

| Disposition | Count | Meaning |
|---|---:|---|
| needs-runtime-hardening | 430 | Concrete evidence found — either no tenant filter at either layer, or a tenant filter that exists but is fed an unvalidated client-supplied value. |
| unresolved | 224 | This single-hop static trace could not determine scoping (no storage/db call detected in the handler, or the call's filtering shape doesn't match the patterns this pass recognizes — e.g. a join, an `IN`-list, or a relational-query-API shape). Not a claim of safety or risk either way. |
| needs-negative-test | 67 | A tenant filter was found and the available evidence suggests it's fed a trusted (session-derived) value — apparently scoped, but not yet covered by an automated cross-tenant regression test. |
| verified-safe | 0 | See note below. |

**Why `verified-safe` is 0, by design, not a tooling gap:** this trace defines
"verified-safe" as *resolved companyId filter, session-derived input, **and**
covered by a passing automated cross-tenant regression test* — not merely
"looks correctly scoped." The codebase has exactly one such test today
(`tests/security.test.ts::testTenantIsolation`, `workers` resource only, per
plan-doc finding T4), and no route in this target set is definitively proven
by it yet. Every route this trace found apparently-scoped-but-unproven is in
`needs-negative-test` instead — that bucket **is** the concrete task list for
Phase 0.5s (add cross-tenant negative tests). `DELETE /api/workers/:id`,
`GET /api/workers`, `GET /api/workers/:id/ytd-taxes`, `PATCH /api/workers/:id`,
and `POST /api/workers` are all in this target set and are the natural first
candidates for 0.5s given the existing test already exercises the `workers`
resource.

Every client-supplied-companyId route that resolved to a scoped storage call
lands in `needs-runtime-hardening`, never `needs-negative-test` — by
definition, a route in this group already has no membership check on its
client-supplied `companyId` (that's why 0.5-B flagged it), so even a
correctly-filtering storage call is being fed a value this trace cannot treat

## Concrete evidence (spot-checked, not inferred)

**`server/storage.ts:1637` — `deleteAccrualAccount(id: string)`:**
```
const [a] = await db.delete(accrualAccounts).where(eq(accrualAccounts.id, id)).returning();
```
No `companyId` parameter, no `companyId` filter. Called by
`DELETE /api/accrual-accounts/:id` (`requireRole("admin")`, no membership
check per the 0.5-B manifest) → `needs-runtime-hardening`.

**`server/routes.ts:18559` — `DELETE /api/commissions/:id`** (manually
read in full to confirm this trace's classification, not just its own
regex signal):
```ts
app.delete("/api/commissions/:id", requireAuth, requireRole("admin", "manager"), async (req, res) => {
  const existing = await storage.getCommission(req.params.id);
  if (!existing) return res.status(404)...;
  if (existing.status === "paid") return res.status(409)...;
  await storage.deleteCommission(req.params.id);
  ...
```
Confirmed by direct reading, not just the automated pass: the handler fetches
by id only, checks `status`, and deletes — no `companyId` comparison anywhere
in the route, and `getCommission`/`deleteCommission` are both id-only in
`storage.ts`. `requireRole("admin", "manager")` is a global role check with no
tenant binding. This is the shape `needs-runtime-hardening` exists to name:
no tenant-scoping mechanism was found at the route or the storage layer —
stated as an evidence-backed inventory finding, not a claim of a demonstrated
exploit.

## Known limitations of this pass (read before treating counts as final)

This is a **single static hop** with a narrow, regex-over-body signal. It
will produce false negatives (marking something `unresolved` or even
`needs-runtime-hardening` when it is in fact safe) in these known shapes,
none of which this trace follows:

1. **Inline ownership checks that don't call a named helper.** 0.5-B's
   (and this trace's) membership-check signal only matches
   `canAccessCompany(`/`assertUserCanAccessCompany(`/`enforceCompanyScope(`.
   A route that manually compares `existing.companyId !== session.companyId`
   inline is invisible to both passes and will be marked
   `needs-runtime-hardening` even if that inline check exists. (The
   `DELETE /api/commissions/:id` example above was manually confirmed to have
   *no* such inline check — but this trace cannot promise every one of the
   430 does not, at scale, without the same manual read.)
2. **Scoping via a join through a different table** (e.g. a resource scoped
   by `workerId` where `workers.companyId` is the actual tenant boundary) —
   not resolved; lands in `unresolved`, not asserted either way.
3. **Scoping enforced by a storage method that itself calls another storage
   method** — this trace does not follow nested storage calls, only the
   route's direct calls.
4. **Handlers registered as a named function reference** rather than an
   inline arrow/function (`app.get(path, mw, someNamedHandler)`) — the AST
   route extractor only captures inline handler bodies; a named-reference
   handler contributes no body text and is `unresolved`.

Given these limitations, **`needs-runtime-hardening` should be read as "no
scoping mechanism was found by this evidence — needs a human to confirm
before writing a fix,"** not as a pre-verified bug list ready for automated
remediation. No route in this document is asserted to have a demonstrated,
exploited vulnerability.

## Recommended next steps (not started in this branch)

1. **Phase 0.5s** — for the 67 `needs-negative-test` routes (prioritize the 5
   `workers` routes given the existing test precedent), add disposable-
   PostgreSQL cross-tenant negative tests per-resource, confirming each is
   actually scoped before it can be reclassified `verified-safe`.
2. A follow-up human review pass over a sample of the 430
   `needs-runtime-hardening` routes to rule out limitation (1) above
   (inline ownership checks this trace can't see) before treating the full
   list as a hardening backlog.
3. Extending the tracer to follow one more hop (nested storage-method calls,
   and join-based scoping) to shrink the 224 `unresolved` bucket, if that
   investment is judged worthwhile before 0.5s begins.

No exploitation steps, request/response payloads, real tenant identifiers, or
customer-identifying data are included in this document or the manifest —
only route/storage-method source locations and static classification
metadata.
